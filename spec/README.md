# 点亮小镇项目规范

本规范适用于在现有项目上继续开发。目标是让不同模型、编辑器和 Agent 执行环境遵循相同的产品、视觉和交付约束。规范不依赖特定模型、Skill、联网服务或专有命令。

## 每次任务的读取顺序

1. 读取项目根目录 `AGENTS.md` 和本文。
2. 根据任务读取下表对应规范及所列源码，检查本次将改变的行为。
3. 使用 [变更模板](CHANGE-TEMPLATE.md) 写明本次范围、行为例子和验收条件，再按小步实现。
4. 执行 [质量门槛](QUALITY.md)，记录实际结果与缺失验证。

|任务|必读规范|实现入口（相对项目根目录）|
|---|---|---|
|全部任务|[产品约束](PRODUCT.md)、[质量门槛](QUALITY.md)|light-town/package.json|
|界面、美术、动效、文案|[设计规范](DESIGN.md)|light-town/src/styles/global.css、light-town/src/art/palette.ts、light-town/src/ui/|
|课程、奖励、计时、题目|[行为规范](BEHAVIOR.md)|light-town/src/config/、light-town/src/core/、light-town/tests/unit/|
|状态、存档、音频、构建|[工程规范](ENGINEERING.md)|light-town/src/app/、light-town/src/core/save/、light-town/scripts/|

## 规则来源与冲突

- 本次用户明确提出的新需求决定本次变更范围；未涉及部分保持本规范和现有体验。
- `spec/` 定义持续维护约束。完整产品数值和内容从 `开发需求描述/产品需求文档.md` 查阅；与其冲突时，`开发需求描述/需求澄清记录.md` 的有效决议优先。
- 配置文件是实现中的数值单一来源；文档与代码不一致时列出具体差异，不能自行将 bug 认定为新需求。
- `light-town/docs/` 中测试报告是有日期的证据，不是对未来版本的通过保证。
- 明显偏离规则的实现应修复；改变课程、经济、存档兼容性或整体视觉方向的产品决策需以用户要求为依据。常规实现细节自行处理。

## 跨模型和 Harness 使用

在 zcode、Claude Code、Codex 或其他工具中，打开整个“点亮小镇”目录。若工具自动读取 AGENTS.md，使用根入口；若只打开 light-town，读取该目录入口。若工具不自动读取项目规则，将 [任务启动提示](START-HERE.md) 粘贴到首条消息。不要假设任意 Harness 会识别同一个私有配置文件。

## 规范维护

每项含行为改变的任务在 `spec/changes/` 创建记录。完成后同步受影响规范、配置、测试和用户说明；最终规则写进对应规范，不要求后续开发者从聊天记录拼出需求。新增规范只放一处，通过链接引用。界面风格有明确变更授权后才更新视觉参照；不得通过替换参照图掩盖意外回归。

[基线清单](baseline.json)记录抽取规范时的关键文件哈希及现有截图路径，用于辨认参照版本，不是不可修改文件名单，也不是测试报告。

## 第二阶段规划

涉及居民任务、中英文课程和长期练习时，读取[第二阶段开发规范](phase-2/README.md)及英文白名单。该规范定义第二阶段开发目标，不改变第一阶段现有规则。

## 双玩家与备份

涉及玩家选择、角色归属、独立进度、自动保存、文件备份恢复或清空时，必读[双玩家与存档规范](players-save/README.md)及[验收清单](players-save/ACCEPTANCE.md)。其玩家作用域、Mac 验证范围和导入导出规则适用于本次功能，第一、第二阶段学习规则保持不变。
